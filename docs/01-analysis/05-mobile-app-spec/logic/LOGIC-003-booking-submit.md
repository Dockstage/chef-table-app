# LOGIC-003 · Создание и безопасный retry брони

**Приоритет:** Critical · **Точка:** BS-001 · **Требования:** FR-005–FR-008, NFR-004, NFR-011, NFR-012 · **Use Case:** UC-01.

## Вход и локальное состояние

Payload: `classId`, `equipmentOption`, `allergyNotes`. Для логической попытки хранится `{key, payloadHash, state}`, где `key` — UUID, а `state` — `submitting`, `unknown` или `final`.

## Алгоритм

1. Проверить выбор, лимит 300 Unicode code points по D-010 и корректность цены.
2. При первом подтверждении текущего payload создать один `Idempotency-Key` и заблокировать CTA.
3. Отправить `createBooking` с Bearer и ключом.
4. При `201` зафиксировать Booking, закрыть BS-001 и открыть SCR-002. Последующий refresh выполняется отдельно: его ошибка не отменяет mutation success.
5. При timeout/обрыве/`500`/`503` считать результат неоднозначным (`unknown`). Повтор того же payload использует тот же ключ.
6. До смены payload после неоднозначного результата сначала разрешить старую попытку replay-запросом или `listBookings`; только после однозначного отсутствия/отказа можно создать новый ключ.
7. После предметного final-отказа изменение payload создаёт новую логическую попытку и новый ключ.

## Ошибки

| Ответ | UI и состояние |
|---|---|
| `401 UNAUTHORIZED` | Final; объяснить проблему доступа, не повторять автоматически |
| `404 CLASS_NOT_FOUND` | Final; закрыть запись и обновить расписание |
| `409 SLOT_FULL` | Final; сохранить ввод, обновить класс, CTA зависит от нового остатка |
| `409 RENTAL_UNAVAILABLE` | Final; сохранить аллергии, обновить класс, предложить own |
| `409 DUPLICATE_BOOKING` | Final; открыть существующую запись в SCR-002 |
| `409 SLOT_NOT_BOOKABLE` | Final; обновить класс, CTA disabled |
| `409 IDEMPOTENCY_CONFLICT` | Ошибка клиента/контракта; не генерировать скрытый retry, зафиксировать диагностику |
| `410 SLOT_CANCELLED` | Final; показать отмену/причину, CTA disabled |
| `422 VALIDATION_ERROR` | Final для payload; связать field errors с полями |
| `429 RATE_LIMITED` | Сохранить попытку; повтор не раньше `Retry-After` с тем же ключом |

## Критерии

- Двойной tap отправляет один запрос.
- Потерянный `201` и повтор не создают вторую бронь и не уменьшают остатки повторно.
- Ошибка refresh после полученного `201` не показывается как ошибка создания.
- Новый payload никогда не отправляется со старым ключом.
