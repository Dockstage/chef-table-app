# LOGIC-001 · Период, даты и фильтрация расписания

**Приоритет:** Critical · **Точки:** SCR-001 · **Требования:** FR-001, FR-002, NFR-007.

## Входы

| Вход | Значения | Источник |
|---|---|---|
| `horizonDays` | `7`, `14`, `30`; default `7` | состояние SCR-001 |
| `selectedDate` | `YYYY-MM-DD` студии | первый день / выбор клиента |
| `level` | `all`, `beginner`, `advanced`; default `all` | выбор клиента |
| `now` | timestamp | системные часы, интерпретация `Europe/Moscow` |
| `classes` | `CookingClass[]` | `listClasses` |

## Алгоритм

1. Построить полуинтервал от начала текущего календарного дня студии до начала дня `+horizonDays` в `Europe/Moscow`.
2. Передать `from`/`to` как ISO 8601 с offset в `listClasses`; смена периода инициирует новый запрос.
3. Построить ровно `horizonDays` date options в зоне студии. При первом входе выбрать первый день.
4. Если прежняя дата вышла из нового диапазона — выбрать первый день; иначе сохранить её.
5. Локально оставить `scheduled`, выбранную дату и выбранный level (`all` не фильтрует уровень).
6. Сортировать результат по `startsAt` по возрастанию.

Изменение level/date не запускает сетевой запрос и не сбрасывает другой фильтр. Отменённые/завершённые классы могут быть получены для истории через `getClass`, но не показываются доступными в SCR-001.

## Ошибки и границы

- Пустой отфильтрованный результат → Empty, не Error.
- Невалидный timestamp/offset → элемент не показывается как доступный; фиксируется диагностическая ошибка без PII.
- Переход месяца/года и DST устройства не меняют московский date key.
- При ошибке нового периода прежний Content сохраняется с прежним диапазоном; см. LOGIC-007.

## Критерии

- Default всегда 7 дней; доступны ровно 14/30 после выбора.
- Level не меняет выбранную дату, дата не меняет level.
- Один и тот же ISO timestamp попадает в дату по `Europe/Moscow`, а не по timezone устройства.
