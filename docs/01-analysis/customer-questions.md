# Вопросы заказчику и зафиксированные ответы

Документ закрывает неоднозначности исходного брифа для текущего учебного MVP. Первоначальное письмо хранится неизменным в `docs/source/brief-cooking.md`; решения, возникшие позже, ссылаются на журнал и ADR.

Внешнего заказчика в учебном проекте нет. Ответы фиксируют выбранные проектные решения и источники, а не имитируют формальную приёмку заказчиком; основание — D-011.

Статусы: **Закрыт** — решение обязательно для MVP; **Отложен** — не блокирует MVP и требует согласования перед production.

## Закрытые вопросы MVP

| ID | Вопрос | Зафиксированный ответ | Статус | Источник |
|---|---|---|---|---|
| Q-001 | Какие роли входят в поставку? | Только клиент. Интерфейсы шефа, владельца и администратора не реализуются. | Закрыт | Бриф, D-004 |
| Q-002 | Как клиент авторизуется? | Для учебного MVP используется seeded demo-клиент и документированная dev Bearer-аутентификация. Production OTP не входит в MVP. | Закрыт | D-004, ADR-001 |
| Q-003 | Какой период расписания показывается? | По умолчанию 7 дней; клиент может расширить период до 14 или 30 дней. | Закрыт | Уточнение R-027 |
| Q-004 | Кто подтверждает наличие места? | Backend в транзакции повторно проверяет остаток и является источником истины; проверка клиента служит только для UX. | Закрыт | Бриф, ADR-001 |
| Q-005 | Сколько мест бронирует один клиент? | Одно место на один аккаунт в одной брони. | Закрыт | Решение MVP |
| Q-006 | Можно ли повторно записаться на тот же класс? | Нет, пока существует активная бронь текущего клиента на этот класс. | Закрыт | BRULE-006 |
| Q-007 | Как работает прокат инвентаря? | Клиент выбирает свой или прокатный набор. Прокат имеет фиксированную доплату и ограничен серверным остатком. | Закрыт | Бриф, R-015 |
| Q-008 | Как передаются сведения об аллергиях? | Свободный необязательный текст до 300 Unicode code points; пустое значение означает отсутствие заявленных аллергий. | Закрыт | Решение MVP, D-010 |
| Q-009 | Как оплачивается класс? | Оплата на месте; онлайн-оплата вне MVP. Деньги в API хранятся в целых копейках. | Закрыт | Бриф |
| Q-010 | Когда клиент может отменить бронь? | Не позднее чем за 12 часов до начала. Ровно за 12 часов отмена разрешена, позже — отклоняется. | Закрыт | Решение MVP |
| Q-011 | Что происходит при отмене студией? | Бронь остаётся в истории со статусом `cancelled_by_studio` и причиной; клиент получает push, повторная запись запрещена. | Закрыт | Уточнение R-008 |
| Q-012 | Какой HTTP-ответ используется для отменённого слота? | `410 Gone` и machine code `SLOT_CANCELLED`. `409 Conflict` используется для занятого места, проката и повторной активной брони. | Закрыт | D-006 |
| Q-013 | Когда можно оценить шефа? | После посещённого класса, один раз: целая оценка 1–5 и необязательный комментарий до 500 Unicode code points. | Закрыт | Бриф, UC-03, D-010 |
| Q-014 | Какие push входят в MVP? | Только уведомление `class_cancelled`. Разрешение запрашивается после явного действия клиента; напоминания о занятии отложены. | Закрыт | Бриф, решение MVP |
| Q-015 | Какие платформы целевые? | Android и iOS; web используется для демонстрации и не обещает нативные push-возможности. | Закрыт | Архитектурное решение |
| Q-016 | В какой зоне считаются даты и дедлайны? | В канонической зоне студии `Europe/Moscow`; API передаёт ISO 8601 с offset. | Закрыт | D-007 |
| Q-017 | Кто создаёт расписание, программы и шефов? | Для клиентского API это read-only данные. В учебном backend они загружаются seed-данными; управляющий UI вне MVP. | Закрыт | Бриф, ADR-001 |
| Q-018 | Зачем реализуется собственный backend, если в брифе он уже существует? | Для воспроизведения полного учебного цикла. Это референсная реализация контракта, а не изменение исходного запроса заказчика. | Закрыт | D-001, ADR-001 |
| Q-019 | Нужны ли лояльность и особые условия постоянным клиентам? | Нет, программа лояльности вне MVP. | Закрыт | Бриф |
| Q-020 | Есть ли исторические/legacy-данные для миграции? | Нет. Миграции создают новую учебную схему, seed формирует демонстрационное состояние. | Закрыт | Уточнение R-015, ADR-001 |

## Отложенные вопросы перед production

| ID | Вопрос | Почему отложен | Что потребуется решить |
|---|---|---|---|
| OQ-001 | Production-авторизация и восстановление доступа | MVP использует dev-auth | OTP-провайдер, TTL, rate limit, refresh/revoke и recovery |
| OQ-002 | Согласие на обработку аллергий | Требует юридического текста | основание обработки, срок хранения, удаление и доступ персонала |
| OQ-003 | Правила поздней отмены и штрафа | В MVP поздняя отмена только блокируется | размер/способ списания и исключения |
| OQ-004 | Production push-провайдер | Нет APNs/FCM-ключей и инфраструктуры | провайдер, токены, retry, delivery status и opt-out |
| OQ-005 | Напоминания о предстоящем классе | Не нужны для основных сценариев сдачи | момент отправки, канал, timezone и настройка пользователя |
| OQ-006 | Глубина истории и пагинация | Demo-данные малы | срок хранения, page/limit/cursor и архивирование |
| OQ-007 | Аналитика и мониторинг | Не влияют на демонстрацию MVP | события без PII, retention, Sentry/metrics и доступы |
| OQ-008 | Production SLA и нагрузка | Учебная среда не моделирует эксплуатацию | целевая доступность, latency percentiles и ожидаемый RPS |
| OQ-009 | Retention idempotency records | В MVP записи живут до сброса учебной БД | срок хранения, безопасная очистка и повтор после истечения |

## Принятые допущения

| ID | Допущение | Проверка перед production |
|---|---|---|
| A-001 | Валюта — российский рубль | подтвердить регион запуска и налоговое отображение цены |
| A-002 | Один аккаунт бронирует одно место | подтвердить необходимость гостевых/групповых броней |
| A-003 | Адрес приходит для каждого класса | подтвердить наличие одной или нескольких площадок |
| A-004 | Статус `attended` выставляет внешняя студийная логика | согласовать источник и момент перехода |
| A-005 | Seeded demo-клиент достаточно идентифицирует учебные запросы | заменить production-auth до реального запуска |
