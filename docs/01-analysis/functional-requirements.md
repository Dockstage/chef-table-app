# Функциональные требования

Функциональные требования задают наблюдаемое поведение клиентского приложения и референсного API. Приоритет указан по MoSCoW; критерий считается выполненным только при подтверждении ожидаемого результата.

| ID | Требование | Критерий приёмки | Приоритет | Источник | Поддерживает |
|---|---|---|---|---|---|
| FR-001 | Показывать расписание на 7, 14 или 30 дней, по умолчанию — 7 | При первом открытии выбран период 7 дней; смена на 14/30 добавляет соответствующий диапазон без потери выбранных фильтров | Must | Q-003; BRULE-002 | BR-001 |
| FR-002 | Фильтровать расписание по дате и уровню | После выбора даты и уровня отображаются только подходящие классы; изменение уровня не сбрасывает дату | Must | Бриф; R-002 | BR-001 |
| FR-003 | Показывать полные детали класса | Карточка содержит программу, меню, шефа, уровень, адрес, начало, длительность, цену, прокат и доступные места | Must | Бриф; R-003; Q-017 | BR-001 |
| FR-004 | Отображать состояния загрузки, результата, отсутствия данных и ошибки | Для каждого запроса расписания пользователь видит ровно одно состояние; при отсутствии классов показано «Пока нет доступных классов», при ошибке доступен повтор | Must | R-011 | BR-001 |
| FR-005 | Собирать данные одной брони | Перед отправкой клиент выбирает свой или прокатный набор и может указать до 300 Unicode code points об аллергиях; бронируется одно место | Must | Q-005; Q-007; Q-008; BRULE-003; BRULE-005; D-010 | BR-001, BR-002 |
| FR-006 | Рассчитывать цену и учитывать прокатный остаток | Итог равен цене класса плюс тариф проката; при нулевом остатке прокат нельзя выбрать или подтвердить | Must | Q-007; Q-009; BRULE-004; BRULE-008 | BR-001, BR-002 |
| FR-007 | Создавать бронь атомарно и идемпотентно | Для активного класса backend в одной транзакции проверяет остатки и уникальность; одинаковый `Idempotency-Key` с тем же payload возвращает исходный результат без второй брони | Must | Q-004; BRULE-006–BRULE-009; D-001 | BR-002 |
| FR-008 | Возвращать различимые ошибки бронирования | Занятое место, недоступный прокат, повторная бронь, иной недоступный статус и конфликт ключа идемпотентности дают `409` с отдельным machine code; отменённый класс даёт `410 SLOT_CANCELLED`; UI показывает понятное действие | Must | Q-012; BRULE-009; BRULE-015; D-006 | BR-002, BR-003 |
| FR-009 | Разделять предстоящие брони и историю | Активные записи показаны в «Предстоящих»; посещённые и отменённые — в «Истории» с актуальным статусом | Must | R-007; BRULE-012 | BR-003 |
| FR-010 | Разрешать клиентскую отмену до дедлайна включительно | Ровно за 12 часов отмена успешна; позднее backend отклоняет её; успешная отмена один раз возвращает место и прокат | Must | Q-010; BRULE-010; BRULE-011 | BR-003 |
| FR-011 | Сохранять результат отмены студией | Связанные брони получают `cancelled_by_studio`, остаются в истории с причиной и не могут быть созданы повторно | Must | Q-011; BRULE-012 | BR-003, BR-004 |
| FR-012 | Принимать отзыв после посещения | Для `attended` один раз принимаются целая оценка 1–5 и комментарий до 500 Unicode code points; для иных статусов и повтора запрос отклоняется | Should | Q-013; BRULE-013; D-010 | BR-005 |
| FR-013 | Регистрировать устройство для push после согласия | Только после явного действия запрашивается системное разрешение; полученный нативный токен связывается с текущим клиентом | Must | Q-014; BRULE-016 | BR-004 |
| FR-014 | Обрабатывать push `class_cancelled` | Foreground, нажатие и cold start приводят к обновлению броней; обработанный cold-start response очищается; отказ в разрешении не блокирует приложение | Must | Q-011; Q-014; R-013 | BR-003, BR-004 |
| FR-015 | Идентифицировать учебного клиента | Защищённые запросы принимают документированный dev Bearer-токен seeded demo-клиента; production OTP не заявляется | Must | Q-002; D-004; ADR-001 | BR-006 |
| FR-016 | Предоставлять только клиентские возможности | Навигация содержит «Классы», «Мои записи» и «Профиль»; создание расписания и интерфейсы шефа/администратора отсутствуют | Must | Q-001; Q-017; R-028; BRULE-001 | BR-006 |

## Общие правила

- Источником окончательного решения о возможности изменения данных является backend.
- Каталог `Chef`, `Program` и `CookingClass` доступен клиенту только для чтения.
- Нерешённые production-вопросы `OQ-001`–`OQ-008` не входят в эти требования.
