# ADR-001 — Собственный backend для учебного проекта

- **Статус:** принято
- **Дата:** 26.09.2026
- **Область:** аналитика, архитектура, разработка и тестирование

## Контекст

Исходный бриф определяет существующий backend как внешний black box, а текущую поставку — как клиентское мобильное приложение и контракт API. Этот исходный текст сохранён без изменений в `docs/source/brief-cooking.md`.

После изучения лекций принято учебное расширение скоупа: воспроизвести полный цикл разработки с отдельными frontend и backend, PostgreSQL, миграциями, seed-данными, Docker и интеграционными тестами. Решение расширяет состав учебной поставки, но не выдаётся за новое требование заказчика.

## Решение

1. Репозиторий будет преобразован в monorepo с каталогами `client/`, `backend/` и общим `docs/`.
2. Существующее Expo/React Native/TypeScript-приложение станет frontend-клиентом.
3. Backend будет реализован на Python 3.12+, FastAPI, Pydantic, SQLAlchemy 2 и PostgreSQL; миграции — Alembic, запуск — Uvicorn.
4. Локальное окружение будет подниматься через Docker Compose; миграции и seed выполняются воспроизводимыми отдельными шагами.
5. Согласованный OpenAPI в `docs/` остаётся контрактным источником истины. Схема, публикуемая FastAPI, должна проверяться на совместимость с ним.
6. В MVP остаётся только роль клиента. Для интеграционных сценариев используется seeded demo-клиент и документированная dev Bearer-аутентификация; production OTP и управление сессиями остаются вне скоупа.
7. Для отменённого студией класса создание брони возвращает `410 Gone` с кодом `SLOT_CANCELLED`; конфликты остатка и повторной брони возвращают `409 Conflict`.
8. Канонический часовой пояс студии — `Europe/Moscow`; API передаёт ISO 8601 с offset, а правила дат считаются в зоне студии.
9. Текущий UI и screenshots используются как дизайн-baseline до появления отдельного Figma-макета.
10. `MockStudioApi` сохраняется только как явно обозначенный demo/test fallback; основной интеграционный путь — `client → FastAPI → PostgreSQL`.

## В скоупе

- чтение расписания и карточки класса;
- создание, просмотр и отмена брони;
- отзыв после посещения;
- регистрация push-токена;
- PostgreSQL-схема, ограничения, миграции и seed;
- атомарность бронирования, отмены и идемпотентного retry;
- Docker Compose, backend unit/API/integration/concurrency tests;
- подключение существующего `HttpStudioApi` к собственному backend.

## Вне скоупа

- интерфейсы и API управления для шефа и администратора;
- создание и редактирование расписания через текущий продукт;
- онлайн-оплата, программа лояльности и чат;
- production OTP, восстановление доступа и полноценное управление сессиями;
- production-доставка APNs/FCM и инфраструктура push-провайдера;
- production deployment и эксплуатационный SLA.

## Последствия

- Производные требования, архитектура, модель данных, OpenAPI, тесты и README должны быть обновлены под собственный backend.
- Гарантии отсутствия двойной брони переходят из предположения о внешней системе в проверяемые транзакции и ограничения нашей БД.
- Появляются две независимые среды зависимостей: Node.js для клиента и Python для backend.
- Объём проекта возрастает; изменения выполняются поэтапно, отдельными TASK/BUG-документами и commits.
- Исходный бриф остаётся неизменным историческим источником.

## Критерии выполнения решения

- `docker compose up --build` поднимает PostgreSQL и FastAPI после документированных подготовительных шагов;
- миграции применяются на пустой базе, seed создаёт воспроизводимые demo-сценарии;
- клиент работает с backend через `EXPO_PUBLIC_API_BASE_URL`;
- контрактные и интеграционные тесты подтверждают основные и ошибочные ветви;
- параллельные запросы не создают двойную бронь и отрицательные остатки;
- документация явно отделяет исходные требования заказчика от учебного расширения.
