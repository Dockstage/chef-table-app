# План реализации клиента

## Цель и исходное состояние

Сохранить работающий Expo/React Native/TypeScript-клиент и привести его к отдельной модульной части monorepo. Уже реализованы восемь пользовательских возможностей, `MockStudioApi`, `HttpStudioApi`, push-модуль и Vitest-тесты. Главные пробелы перечислены в [`lecture-gap-checklists.md`](../lecture-gap-checklists.md): монолитный `App.tsx`, нестабильный retry, смешение mutation/refresh, неполные error states и недостаточная проверка входящих данных.

## Целевая структура

```text
client/
  App.tsx
  src/
    app/
    domain/
    data/
    features/
      schedule/
      booking/
      bookings/
      review/
      profile/
    notifications/
    shared/ui/
    shared/theme/
  tests/
```

`App.tsx` остаётся composition root. UI, application state, API adapters и чистые бизнес-правила не смешиваются в одном файле.

## Итерационный чеклист

### CL-00 — Перенос в monorepo без изменения поведения

- [ ] Один раз зафиксировать исходный результат `typecheck`, тестов и web export.
- [ ] Перенести Expo-файлы, `src/`, `tests/` и Node manifests в `client/`.
- [ ] Обновить `.gitignore`, README, пути команд и ссылки; общие `docs/` оставить в корне.
- [ ] Повторить те же проверки из `client/` и подтвердить отсутствие функциональных изменений.

### CL-01 — Инструменты качества

- [ ] Добавить ESLint и Prettier с командами `lint` и `format:check`.
- [ ] Проверить Expo-совместимость зависимостей и задокументировать результат `npm audit` без `--force`.
- [ ] Добавить client-проверки в CI после стабилизации структуры.

### CL-02 — Модульная архитектура

- [ ] Вынести theme и переиспользуемые UI primitives.
- [ ] Разделить экраны и overlays по feature-модулям.
- [ ] Вынести orchestration и навигацию из UI-компонентов.
- [ ] Обновить `docs/02-design/architecture.md` по фактической структуре.

Готово, когда `App.tsx` только собирает приложение, а feature-модули не импортируют детали друг друга напрямую.

### CL-03 — Безопасная граница API

- [ ] Синхронизировать `ApiErrorCode` и DTO со всеми ответами OpenAPI.
- [ ] Валидировать входящий JSON вместо безусловных TypeScript casts.
- [ ] Проверять rating 1–5, allergies до 300 и comment до 500 во всех data adapters.
- [ ] Зафиксировать `Europe/Moscow` для запросов, группировки и отображения дат.

### CL-04 — Модель состояний и загрузка

- [ ] Ввести `initial/loading/content/empty/error/refreshing` и постоянный initial error с «Повторить».
- [ ] Сохранять контент при refresh failure.
- [ ] Не срывать весь экран из-за недоступной карточки одной архивной брони.
- [ ] Разделить состояние submit и фонового обновления.

### CL-05 — Надёжное бронирование

- [ ] Генерировать один `Idempotency-Key` на payload и повторно использовать его после неопределённого сетевого результата.
- [ ] Сбрасывать ключ при изменении payload либо однозначном завершении операции.
- [ ] После `SLOT_FULL`, `SLOT_CANCELLED` и `RENTAL_UNAVAILABLE` обновлять класс, сохраняя допустимые поля формы.
- [ ] Успешную бронь считать успешной даже при последующей ошибке refresh.

Готово, когда сценарий «backend создал бронь, ответ потерян» не создаёт вторую запись.

### CL-06 — Отмена и отзыв

- [ ] После успешной отмены сразу применять серверный результат, затем отдельно обновлять данные.
- [ ] При конфликте повторной отмены обновлять детали и показывать предметное сообщение.
- [ ] Проверить одноразовый отзыв, границы rating/comment и историю отмен студией.

### CL-07 — Push-контракт

- [ ] Проверять `type`, `bookingId` и `reason` до обработки уведомления.
- [ ] Использовать `bookingId` для адресного обновления/навигации.
- [ ] Сохранить web fallback и явно отделить его от нативной доставки APNs/FCM.

### CL-08 — Доступность и честные affordance

- [ ] Обеспечить touch target не меньше 44×44.
- [ ] Добавить роли, selected state и доступные названия элементов.
- [ ] Реализовать действия строк с chevron либо убрать вид нажимаемого элемента.
- [ ] Проверить keyboard, long text, font scaling, safe areas и narrow viewport.

### CL-09 — Интеграция с FastAPI

- [ ] Подключить локальный backend через `EXPO_PUBLIC_API_BASE_URL`.
- [ ] Оставить `MockStudioApi` только как явно выбранный demo/test fallback.
- [ ] Пройти расписание → бронь → конфликт/retry → отмена → отзыв → push token.
- [ ] Проверить web и минимум одну нативную среду, если она доступна.

### CL-10 — Финальный client gate

- [ ] Выполнить clean install, typecheck, lint, tests и web export.
- [ ] Обновить трассировку, README и чеклист только по фактическому результату.
- [ ] Зафиксировать ограничения нативного push и непроверенных платформ.

## Зависимости между планами

`CL-00` выполняется до активной backend-разработки. `CL-01`–`CL-04` можно выполнять параллельно логически, но последовательно в Git. `CL-05`–`CL-07` сверяются с соответствующими `BE-05`–`BE-07`. `CL-09` начинается только после миграций, seed и нужных endpoint backend.

## Правило итерации

Каждый `CL-*` получает TASK/PROMPT, минимальное изменение, релевантные тесты и focused commit. Полный suite не запускается повторно, если после его результата не менялись влияющие файлы.
